# Local profile reference and bootstrap design candidate

**Status:** `PROPOSED_REVIEW_PENDING`, `NON_CLAIMABLE`. This is a bounded integration design candidate based on `0f691f1b3fd10755a3c8e650ddea6f9311842978`. It creates no accepted type or record kind, profile instance, actor registration, credentials, keys, authority, qualification, signatures, ticket, lease, launch change, or `PASS` result. The two TOMLs beside this note describe proposed contracts only.

The candidate closes two design gaps without depending on a package ticket, package submission, or running Search process: a qualified slash-separated profile reference has an exact bounded grammar, and a bootstrap evidence path can register and review actors before the package workflow exists. Actual trust still starts from a current root pin delivered by an externally authorized channel. This note does not invent that channel or root.

## Qualified profile reference

The proposed alias `QualifiedProfileRefV1` is the complete `QualifiedOpaqueId` value:

```text
namespace "/" local_opaque_id
```

`namespace` is 1–96 ASCII bytes matching `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`. `local_opaque_id` is 1–128 exact, case-sensitive ASCII bytes matching the existing `OpaqueId` grammar `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`. There is exactly one literal `/`, no empty component, no other separator, no whitespace, Unicode, URL encoding, escape, normalization, or case folding. The full value is at most 225 ASCII bytes. The repository/project namespace must be checked against an explicitly accepted project/profile registry binding; it is never inferred from a Git remote, checkout name, or display name. Parsing syntax alone does not establish registration or qualification.

This proposal binds the exact grammar to both existing rules in `swarm/schemas/types-v1.toml`: `ImmutableArtifactRef.store_profile_ref_is_qualified_opaque_id` and `ImmutableSignatureRef.approval_profile_ref_is_qualified_opaque_id`. Each rule must validate the complete value using `QualifiedOpaqueId`; the slash is permitted only as the single namespace delimiter, and both components are checked independently. The existing `OpaqueId` definition remains unchanged. Current syntax examples such as `eliot-search/local-git-sha256-artifact-store-v1` and `eliot-search/local-windows-cng-software-ecdsa-p256-v1` are not registered or qualified profiles.

At base `0f691`, `OpaqueId` itself forbids `/` and no `QualifiedOpaqueId` definition exists. Thus the named `*_profile_ref_is_qualified_opaque_id` rule is not yet an accepted grammar or proof that current consumers handle the separator. The type registry and each consumer need integration-owner acceptance and conformance evidence before runtime use.

## Bootstrap cycle and record boundary

The current `ClosedControlRecordKind` set is exactly `context_manifest_v1`, `assignment_ticket_v1`, `writer_lease_v1`, `lease_event_v1`, `package_submission_v1`, `independent_review_v1`, `package_handoff_v1`, and `supersession_receipt_v1`; it has no actor-registration or qualification-bootstrap kind. In particular, using `package_submission_v1` or `independent_review_v1` to establish the approval profile would be circular: those records sit downstream of issued ticket and package work. This proposal does not add an item to that closed set or reinterpret either existing kind.

Instead, `bootstrap-evidence-v1.toml` proposes a small, separately versioned set of public bootstrap artifacts under `swarm/profile-bootstrap/v1/`. Their references are proposal-local `BootstrapEvidenceRefV1` and `BootstrapReviewBindingRefV1`, not `ImmutableRecordRef` and not closed control records. A reference binds the exact repository identity, full commit OID, repository-relative path, full tagged Git blob ID, exact byte count, independent SHA-256, and closed bootstrap artifact kind. Reads resolve only within the named commit tree. They reject a symlink/non-blob, filters, alternate path spelling, traversal, object-format mismatch, byte-count mismatch, Git blob mismatch, or SHA-256 mismatch. Content-addressed objects are create-only; identical bytes may be reused after exact readback, while a mismatch is an integrity failure.

The evidence manifest and all raw outcomes are committed together. The outer evidence reference is computed only after that commit exists. A separate reviewer task then writes the signed review binding and its raw review output in a later commit. This avoids self-commit references. The evidence and review use domain-separated signatures over exact pre-signature bytes; each signature trailer is outside its own signed body. Other signed records created in a probe may be outputs, but a record never includes its own signature artifact or digest in its own preimage.

The proposed fixed binary framing is recorded in the TOML: exact magic, version, field count, ordered TLVs (`u16be ordinal`, `u8 type`, `u32be value length`, exact bytes), explicit nested-record/array/optional encodings, and rejection of unknown, repeated, missing, reordered, truncated, overlong, and trailing bytes. Evidence contains exactly one ordered result for every closed mandatory probe ID. `UNAVAILABLE`, `PASS`, and `FAIL` remain distinct; `PASS` and `FAIL` require bound raw output, and `UNAVAILABLE` carries a reason without pretending an output exists. Every limit is finite, including envelope, manifest, individual and aggregate raw-output, memory, and operation/recovery bounds. The proposal's probe results are all `UNAVAILABLE` and `executed = false`.

## Trust root and actor bootstrap

The trust root is not a key found in Git. Each future authoritative bootstrap or activation must receive an explicit `--expected-root-key-id sha256-<64 lowercase hex>` from the caller. The expected pin must come from the actual externally authorized authority channel, with its currentness/authenticated-delivery process confirmed by that caller. “Out of band” identifies this authority channel outside the signed Git record; it does not imply another OS account or a physical cryptographic ceremony. The native tool also receives an explicit `--authority-envelope <file>`, checks its bounded canonical bytes, checks that its root ID equals the supplied pin, hashes the exact 72-byte P-256 public BCRYPT blob, and verifies the root signature over the exact domain-separated preimage. A self-signed envelope, repository default, environment fallback, local username, display name, matching hash without the externally supplied pin, missing channel, or unverifiable freshness fails closed as `UNAVAILABLE`. The channel label and authorization artifact digest are trace metadata, not channel proof. The tool cannot query external revocation or prove the channel fresh; absence of a trustworthy current pin blocks authority.

The root-signed envelope maps exactly two exact `ActorIdentity` values and public keys: one `bootstrap_operator` and one `independent_reviewer`. Identities and key IDs must differ, the reviewer identity must have the existing `reviewer` actor class, and the integration owner explicitly assigns distinct operator/reviewer task IDs before the run; the reviewer task cannot be the operator task and needs no package ticket. The envelope grants only the two bootstrap domains to those respective roles. It does not grant ticket-issuance domains or mark the approval profile qualified.

The local signing candidate is Windows CNG's Microsoft Software Key Storage Provider with persisted current-user ECDSA P-256 keys. Key creation is create-only, does not use the machine-key flag or overwrite flag, rejects an existing container, records only exact public blobs and non-secret readback, and has no provider fallback. `NCRYPT_SILENT_FLAG` makes a UI-required signing request fail closed. A future qualification must prove provider behavior, export denial and independent verifier agreement; setting/readback of the export policy alone is not that proof. The proposed signature wire encoding is 64-byte IEEE P1363 `r[32] || s[32]`, which is an explicit candidate requiring probes, not a claim established by the API documentation.

The software baseline assumes a trusted cooperative local host/launcher and explicit role assignment. Distinct mapped IDs, public keys, and separate writer/reviewer tasks support cryptographic attribution, but same-Windows-user processes can request keys available to that account. This does not prove process or human isolation. The normative requirement is distinct writer/reviewer identities and actual independent review; separate OS accounts and hardware are not baseline prerequisites. Stronger custody can be qualified as an optional profile. No key generation, account setup, device enrollment, or trust bootstrap occurred here.

The root envelope itself is an external authorization input; it can be copied into the evidence commit for byte-level audit, but Git does not create its authority. After evidence and independent review exist, an externally authorized root signer may publish the proposed versioned actor-trust manifest and head. The manifest contains exact actor mappings and the immutable evidence/review references; the head names the manifest's exact outer locator. The head's current locator is one explicitly bound full `refs/heads/...` ref and repository identity. Each authoritative operation resolves that ref to its full commit OID, reads the exact head from that commit tree, verifies root pin/signatures, manifest blob and file digests, and generation. Updates publish the immutable manifest first, then compare-and-swap the same ref from the exact expected old commit to the head-containing commit and read it back. A timeout after a possible ref update is `OUTCOME_UNKNOWN` until exact readback resolves it. This is local one-repository/ref currentness, not remote-global or cross-clone currentness.

Root rotation and external revocation are not silently handled: v1 has no rotation procedure. A changed/revoked pin invalidates the trust snapshot; until a separately reviewed rotation/currentness contract and new externally supplied pin exist, authoritative use remains unavailable. Adding the proposed trust snapshot records/schema to accepted registries is also an integration-owner action, not part of this candidate.

## Minimal standalone sequence

1. An integration owner or authorized operator obtains the actual current root public blob and expected fingerprint from the external authority channel, confirms its authorization/currentness outside the Git record, and supplies the pin explicitly. No pin or uncertain freshness stops the procedure.
2. Under the trusted cooperative host assumption, the integration owner assigns exact operator and reviewer actor/task IDs. The operator provisions its current-user software-key container; a separate reviewer task provisions the reviewer container. Both send exact actor IDs, public blobs, and container labels to the actual authority through its authorized process. The authority owner verifies the request and returns a root-signed envelope mapping both actor/key pairs with bootstrap-only domains. This does not infer identity from names or hashes.
3. The operator supplies the exact pin and returned envelope to the native bootstrap tool. It verifies the envelope, runs the bounded probes, captures exact inputs/outputs and runtime identities, and signs the evidence body with the mapped operator key. One Git commit contains the canonical evidence manifest, envelope copy, and create-only raw blobs. No ticket, lease, submission, Search process, or control-record kind is required.
4. A separate reviewer task resolves the outer evidence reference only after its commit exists; verifies the exact bytes and root mapping; replays the specified checks with a separately identified verifier; and writes a signed, bounded review binding in a later commit. Its reference binds the exact evidence commit, file digest, actor IDs, reviewed probe IDs, raw review output, and verifier executable digest.
5. The externally authorized root signer verifies the exact evidence and review refs. Only after a separately accepted profile definition and qualification can the integration owner accept a trust-manifest/head schema and have the authorized root publish a trust snapshot for explicitly permitted operation domains. A bootstrap-only envelope does not become operational approval authority by itself.
6. Integration-owner acceptance of the type grammar, bootstrap artifact shapes, activation snapshot, profile definition/instance, and executed qualification evidence remains a separate necessary decision. Until then every candidate is non-claimable and no issuance operation is authorized.

This order breaks the bootstrap cycle without pretending that the bootstrap evidence is itself an accepted `independent_review_v1` or qualification record. The exact unavailable inputs are the real external authority identity/channel and current pin, that authority's signed actor mapping, the two future local public-key readbacks, exact repository/runtime hashes, an independently identified verifier, raw executed outcomes, an integration-owned retention/recovery policy, and later integration-owner registry/profile acceptance.

## Boundaries and qualification

The design uses Git blobs, trees, commits, and an exact-ref compare-and-swap, consistent with ADR 0003's accepted Git-plus-append-only-receipt direction. Git documents that `update-ref <ref> <new-oid> <old-oid>` changes a ref only if the current value equals the supplied old OID ([git-update-ref](https://git-scm.com/docs/git-update-ref), current documentation checked 2026-10-03). Git's `hash-object --no-filters` option ignores content filters, including end-of-line conversion ([git-hash-object](https://git-scm.com/docs/git-hash-object), current documentation checked 2026-10-03); the candidate still requires explicit exact-byte readback and tree resolution. It proposes no orchestration service, database, Governor or Memory OS dependency, runtime package implementation, dependency installation, or network publication. The earlier local issuance profiles remain separate drafts and were not edited by this follow-up.

The required qualification suite is listed in the candidate TOML and is not executed. It includes `QualifiedProfileRefV1` grammar and existing-consumer fail-closed behavior; missing/mismatched pin and self-signature rejection; canonical encoding and digest mutation; identity-to-key mapping; create-only key creation and exact public readback; export denial; CNG P1363 agreement with an independent verifier; domain/payload and malformed-TLV rejection; content-addressed Git readback; head currentness/CAS; independent reviewer binding; operation without ticket/submission/Search; same-user key reachability without isolation claims; and stale/missing external authority. No probe is reported as `PASS`.
