# Local profile reference and bootstrap design candidate

**Status:** `PROPOSED_REVIEW_PENDING`, `NON_CLAIMABLE`. This is a bounded integration design candidate based on `0f691f1b3fd10755a3c8e650ddea6f9311842978`. It creates no accepted type or record kind, profile instance, actor registration, credentials, keys, authority, qualification, signatures, ticket, lease, launch change, or `PASS` result. The two TOMLs beside this note describe proposed contracts only.

The candidate closes two design gaps without depending on a package ticket, package submission, or running Search process: a qualified slash-separated profile reference has an exact bounded grammar, and a bootstrap evidence path can register and review actors before the package workflow exists. The baseline trust root is provisioned, inspected and pinned by an authorized integration owner through a distinct explicit owner action in protected host/launcher state outside the product Git repository. This proposal has no actual root key or host pin state and creates neither one.

## Qualified profile reference

The proposed alias `QualifiedProfileRefV1` is the complete `QualifiedOpaqueId` value:

```text
namespace "/" local_opaque_id
```

`namespace` is 1–96 ASCII bytes matching `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`. `local_opaque_id` is 1–128 exact, case-sensitive ASCII bytes matching the existing `OpaqueId` grammar `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`. There is exactly one literal `/`, no empty component, no other separator, no whitespace, Unicode, URL encoding, escape, normalization, or case folding. The full value is at most 225 ASCII bytes. The repository/project namespace must be checked against an explicitly accepted project/profile registry binding; it is never inferred from a Git remote, checkout name, or display name. Parsing syntax alone does not establish registration or qualification.

This proposal binds the exact grammar to both existing rules in `swarm/schemas/types-v1.toml`: `ImmutableArtifactRef.store_profile_ref_is_qualified_opaque_id` and `ImmutableSignatureRef.approval_profile_ref_is_qualified_opaque_id`. Each rule must validate the complete value using `QualifiedOpaqueId`; the slash is permitted only as the single namespace delimiter, and both components are checked independently. The existing `OpaqueId` definition remains unchanged. Current syntax examples such as `eliot-search/local-git-sha256-artifact-store-v1` and `eliot-search/local-windows-cng-software-ecdsa-p256-v1` are not registered or qualified profiles.

At base `0f691`, `OpaqueId` itself forbids `/` and no `QualifiedOpaqueId` definition exists. Thus the named `*_profile_ref_is_qualified_opaque_id` rule is not yet an accepted grammar or proof that current consumers handle the separator. The type registry and each consumer need integration-owner acceptance and conformance evidence before runtime use.

## Bootstrap cycle and record boundary

The current `ClosedControlRecordKind` set is exactly `context_manifest_v1`, `assignment_ticket_v1`, `writer_lease_v1`, `lease_event_v1`, `package_submission_v1`, `independent_review_v1`, `package_handoff_v1`, and `supersession_receipt_v1`; it has no actor-registration or qualification-bootstrap kind. In particular, using `package_submission_v1` or `independent_review_v1` to establish the approval profile would be circular: those records sit downstream of issued ticket and package work. This proposal does not add an item to that closed set or reinterpret either existing kind.

Instead, `bootstrap-evidence-v1.toml` proposes a small, separately versioned set of public bootstrap artifacts under `swarm/profile-bootstrap/v1/`. Their references are proposal-local `BootstrapEvidenceRefV1` and `BootstrapReviewBindingRefV1`, not `ImmutableRecordRef` and not closed control records. A reference binds the exact repository identity, full commit OID, repository-relative path, full tagged Git blob ID, exact byte count, independent SHA-256, and closed bootstrap artifact kind. Reads resolve only within the named commit tree. They reject a symlink/non-blob, filters, alternate path spelling, traversal, object-format mismatch, byte-count mismatch, Git blob mismatch, or SHA-256 mismatch. Content-addressed objects are create-only; identical bytes may be reused after exact readback, while a mismatch is an integrity failure.

The evidence manifest and all raw outcomes are committed together. The outer evidence reference is computed only after that commit exists. A separate reviewer task then writes the signed review binding and its raw review output in a later commit. This avoids self-commit references. The evidence and review use domain-separated signatures over exact pre-signature bytes; each signature trailer is outside its own signed body. Other signed records created in a probe may be outputs, but a record never includes its own signature artifact or digest in its own preimage.

The proposed fixed binary framing is recorded in the TOML: exact magic, version, field count, ordered TLVs (`u16be ordinal`, `u8 type`, `u32be value length`, exact bytes), explicit nested-record/array/optional encodings, and rejection of unknown, repeated, missing, reordered, truncated, overlong, and trailing bytes. Evidence contains exactly one ordered result for every closed mandatory probe ID. `UNAVAILABLE`, `PASS`, and `FAIL` remain distinct; `PASS` and `FAIL` require bound raw output, and `UNAVAILABLE` carries a reason without pretending an output exists. Every limit is finite, including envelope, manifest, individual and aggregate raw-output, memory, and operation/recovery bounds. The proposal's probe results are all `UNAVAILABLE` and `executed = false`.

## Trust root and actor bootstrap

The root trust is not a key found in Git and is not created by the bootstrap command. Before bootstrap, the authorized integration owner performs a distinct explicit action on the trusted localhost: provision or select the root signing key, inspect its exact public BCRYPT blob and computed fingerprint, and pin a bounded record in ACL-protected host/launcher state outside the product repository. The launcher path is configured explicitly and is not derived from Git, environment, username or checkout. No external signing service, second human, hardware token or new service is required by this baseline.

Every authoritative bootstrap, review or activation operation receives an explicit `--expected-root-key-id sha256-<64 lowercase hex>`. It freshly reads the protected current pointer and its immutable pin record, verifies their canonical bytes, ACL, generation and digests, hashes the exact 72-byte P-256 public blob, and requires the result to equal both the supplied pin and the signed envelope/head root. A self-signed envelope, repository default, environment fallback, local username, display name, stale cache, inactive pointer or mismatched fingerprint fails closed as `UNAVAILABLE`. The host OS and configured ACL provide authenticated local currentness under the declared trusted-host assumption; these checks do not protect against compromise of the authorized host or token. External channel labels and reference digests remain trace metadata. An external authority channel or remote revocation check may be added by an optional stronger profile, but neither is a standalone-baseline prerequisite.

The host pin record is bounded to 4 KiB, canonical UTF-8/LF, and stores the project namespace, generation, root ID, exact public blob and an owner-action identifier. Immutable generation records are created only once and read back byte-for-byte. A protected current pointer selects the active generation. The owner and launcher ACLs are checked through the final file handles; broad write access, unexpected inheritance, reparse points or a path outside the configured state root fail closed. Every operation reads the pointer and record afresh and holds a shared state lock through its authority check; owner rotation takes the exclusive lock. Initial pinning is create-only. To rotate, the owner first marks the pointer `ROTATION_PENDING`, provisions and inspects a new key, creates and reads back generation `n+1`, then atomically switches the pointer. Any error leaves authority unavailable without falling back to the old pin. Old records remain for audit, but old-root envelopes and snapshots cannot authorize new work. If the authorized owner and launcher share a Windows token, every process with that token can reach account keys and state; the profile makes no process-isolation or distinct-human claim.

The locally root-signed envelope maps exactly two exact `ActorIdentity` values and public keys: one `bootstrap_operator` and one `independent_reviewer`. Identities and key IDs must differ, the reviewer identity must have the existing `reviewer` actor class, and the integration owner explicitly assigns distinct operator/reviewer task IDs before the run; the reviewer task cannot be the operator task and needs no package ticket. The v1 canonical field order is unchanged; the envelope's authority-channel fields are trace metadata only. The envelope grants only the two bootstrap domains to those respective roles. It does not grant ticket-issuance domains or mark the approval profile qualified.

The local signing candidate is Windows CNG's Microsoft Software Key Storage Provider with persisted current-user ECDSA P-256 keys. Key creation is create-only, does not use the machine-key flag or overwrite flag, rejects an existing container, records only exact public blobs and non-secret readback, and has no provider fallback. `NCRYPT_SILENT_FLAG` makes a UI-required signing request fail closed. A future qualification must prove provider behavior, export denial and independent verifier agreement; setting/readback of the export policy alone is not that proof. The proposed signature wire encoding is 64-byte IEEE P1363 `r[32] || s[32]`, which is an explicit candidate requiring probes, not a claim established by the API documentation.

The software baseline assumes a trusted cooperative local host/launcher and explicit role assignment. Distinct mapped IDs, public keys, and separate writer/reviewer tasks support cryptographic attribution, but same-Windows-user processes can request keys and state available to that account. This does not prove process or human isolation. The normative requirement is distinct writer/reviewer identities and actual independent review; separate OS accounts and hardware are not baseline prerequisites. Stronger custody can be qualified as an optional profile. No root or actor key generation, account setup, device enrollment, host pinning or trust bootstrap occurred here.

The root envelope is created and signed during an explicit integration-owner action against the active host-pinned root; it can be copied into the evidence commit for byte-level audit, but Git does not create its authority. After evidence and independent review exist, the local root signer may publish the proposed versioned actor-trust manifest and head. The manifest contains exact actor mappings and the immutable evidence/review references; the head names the manifest's exact outer locator. The head's current locator is one explicitly bound full `refs/heads/...` ref and repository identity. Each authoritative operation resolves that ref to its full commit OID, reads the exact head from that commit tree, verifies the root against both the explicit caller pin and fresh protected host state, and verifies signatures, manifest blob/file digests and generation. Updates publish the immutable manifest first, then compare-and-swap the same ref from the exact expected old commit to the head-containing commit and read it back. A timeout after a possible ref update is `OUTCOME_UNKNOWN` until exact readback resolves it. This is local one-repository/ref currentness, not remote-global or cross-clone currentness.

The accepted review, evidence and activation snapshot must all bind the exact same `QualifiedProfileRefV1` and definition digest. The profile-reference namespace must equal both the envelope and evidence project namespace. Evidence names an exact candidate present in the root-signed envelope. Operator and reviewer identities, key IDs, containers and public blobs must match the corresponding envelope rows; evidence task IDs are explicit, and the review task ID must equal the reviewer task ID and differ from the operator task. The activation snapshot repeats the exact actor/key mappings and evidence/review refs. Before approval-profile use, the separately maintained approval-profile definition must adopt these exact refs, profile digest and active trust-snapshot/root generation binding. This change does not edit that parent draft.

Root replacement never overwrites an existing record and never silently falls back. The explicit owner rotation contract marks the current pointer `ROTATION_PENDING`, creates and verifies the next immutable record, then switches the pointer atomically; any failure keeps operations unavailable. The baseline does not provide remote-global revocation. Adding the proposed trust snapshot records/schema to accepted registries and adopting the exact bootstrap refs/digest in the approval profile are integration-owner actions outside this candidate.

## Minimal standalone sequence

1. Through a distinct explicit owner action outside bootstrap and outside Git, the authorized integration owner provisions or selects the root key, inspects its exact public blob and computed fingerprint, and create-only pins a bounded record in protected host/launcher state with exact ACL and readback. No root key or host state exists in this proposal.
2. The operator or reviewer supplies the expected root fingerprint explicitly for each authoritative operation. The native command freshly reads the active protected host pin, checks its ACL, canonical bytes, generation and exact public-blob digest, and compares that state with the caller pin and envelope. Missing, stale or uncertain state stops the operation.
3. The integration owner explicitly assigns operator/reviewer actor and task IDs and exact key-container names. The operator and reviewer provisioning actions read back their public keys, then a separate explicit local owner action signs the v1 envelope mapping those exact actor/key pairs and bootstrap-only domains. Its canonical field order is preserved and its authority-channel fields are trace metadata. No identity is inferred from a name or hash.
4. The operator supplies the exact pin and envelope. The native bootstrap tool verifies them, executes the bounded probes, captures exact inputs/outputs and runtime identities, and signs the evidence body with the mapped operator key. One Git commit contains the canonical evidence manifest, envelope copy and create-only raw blobs. No ticket, lease, submission, Search process or control-record kind is required.
5. A separate reviewer task resolves the outer evidence reference only after its commit exists, checks the exact profile/digest, root, actor/key and task bindings with a separately built verifier, and writes a signed bounded review binding in a later commit. Its review task ID equals the evidence reviewer task ID and differs from the operator task ID.
6. The local root signer verifies the exact evidence and review refs. Only after a separately accepted profile definition and qualification can the integration owner accept a trust-manifest/head schema and publish a trust snapshot for explicitly permitted operation domains. The later approval-profile definition must adopt the exact profile ref, definition digest, evidence/review refs and trust-snapshot/root generation before issuance use.
7. Integration-owner acceptance of the type grammar, bootstrap artifact shapes, activation snapshot, profile definition/instance and executed qualification evidence remains a separate necessary decision. Until then every candidate is non-claimable and no issuance operation is authorized.

This order breaks the bootstrap cycle without pretending that the bootstrap evidence is itself an accepted `independent_review_v1` or qualification record. The exact unavailable inputs are the actual owner-provisioned root key and host pin state/ACL, the signed local actor mapping, future actor-key readbacks and task assignments, exact repository/runtime hashes, an independently identified verifier, raw executed outcomes, an integration-owned retention/recovery policy, and later integration-owner registry/profile acceptance. An external authority channel is required only if an optional stronger profile is selected.

## Boundaries and qualification

The design uses Git blobs, trees, commits, and an exact-ref compare-and-swap, consistent with ADR 0003's accepted Git-plus-append-only-receipt direction. Git documents that `update-ref <ref> <new-oid> <old-oid>` changes a ref only if the current value equals the supplied old OID ([git-update-ref](https://git-scm.com/docs/git-update-ref), current documentation checked 2026-10-03). Git's `hash-object --no-filters` option ignores content filters, including end-of-line conversion ([git-hash-object](https://git-scm.com/docs/git-hash-object), current documentation checked 2026-10-03); the candidate still requires explicit exact-byte readback and tree resolution. It proposes no orchestration service, database, Governor or Memory OS dependency, runtime package implementation, dependency installation, or network publication. The earlier local issuance profiles remain separate drafts and were not edited by this follow-up.

The required qualification suite is listed in the candidate TOML and is not executed. It includes `QualifiedProfileRefV1` grammar and existing-consumer fail-closed behavior; explicit-pin/host-state equality and ACL/readback/rotation rejection; self-signature rejection; canonical encoding and digest mutation; namespace, candidate allowlist, cross-profile, profile-digest, actor/key and task substitution rejection; create-only key creation and exact public readback; export denial; CNG P1363 agreement with an independent verifier; domain/payload and malformed-TLV rejection; content-addressed Git readback; head currentness/CAS; independent reviewer binding; operation without ticket/submission/Search; and same-user key reachability without isolation claims. No probe is reported as `PASS`.
